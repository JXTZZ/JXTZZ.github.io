    Hello-Agents：从零开始构建智能体 · 章节学习笔记

    原作：Datawhale Hello-Agents 项目及贡献者
    原文章节：第 5 章正文

    引言¶

    前一章把循环、计划和反思都写进了 Python。现在，假设业务同事也想调整信息来源、输出格式或处理顺序，每次都修改代码就不一定方便了。

    低代码平台把不少通用工作封装成节点和配置。本章通过四个平台的案例，讨论怎样从画布上的连线看懂真正的数据流，以及这些封装在什么地方仍需要开发者作判断。

    5.1　低代码省下了哪些工作¶

    模型调用、插件连接、知识库和运行记录，在不同应用里经常重复出现。平台将这些能力放进可配置组件，让我们先关注信息从哪里来、交给谁处理、最后送到哪里。

    这也让产品和业务人员更容易参与。一个节点写错了输出字段，下游依然会失败；模型误解了要求，画布也不会自动纠正。低代码减少了部分实现工作，数据约定与任务设计仍然需要想清楚。

    本章的平台界面和插件能力，来自原文对应版本。阅读时更值得保留的是流程结构，不必记住某张截图里按钮所在的位置。

    5.1.1　把画布看成数据转换，而不只是连线¶

    每个节点都有输入、输出和配置。输入来自上游或用户，配置规定处理方式，输出再进入后续节点。调试时先看某个字段的值怎样变化，通常比从头重新配置整个应用更有效。

    例如，资讯插件可能返回 title、url 和正文列表，生成节点却只接收了标题。此时模型没有看到正文，无论怎样强调“总结准确”，也很难完成需要正文依据的摘要。问题发生在数据映射，而不一定是提示不够强。

    可以先用固定小数据逐个运行节点，再接真实接口。这样能分开检查连线、字段和外部服务，定位失败也更清楚。可视化平台让关系容易看见，仍需我们确认每条线传递了什么。

    5.2　Coze：从多种信息源生成每日简报¶

    原文的“每日 AI 简报”从媒体、GitHub 和 arXiv 等来源获取内容，再整理成统一形式。这个例子把插件、提示和工作流接在一起。

    示例 5.1　沿着一条资讯走一遍

    插件取得资讯或论文信息
  → 提取标题、时间、来源和正文要点
  → 合并相近内容，筛选与主题有关的条目
  → 按约定格式生成简报
  → 预览并发布到选定渠道

    模型需要知道什么算重要信息，以及摘要应保留哪些内容。插件返回很多字段时，最好先统一结构，否则下游要为每个来源写不同的处理逻辑。

    5.2.1　插件能力与提示约束¶

    角色设定帮助说明任务，插件提供实际数据。两者缺一，效果都会受限：只有提示，无法知道当天发生了什么；只有数据，没有筛选要求，也可能生成一份杂乱的汇总。

    Coze 案例体现的是快速组合与发布的便利。实际接入仍取决于插件是否可用、授权是否有效，以及返回的数据能否满足需要。平台能力持续变化，不能把原文的功能比较当作永久结论。

    5.2.2　从多源列表到一份统一简报¶

    媒体新闻、论文和开源项目的原始结构不同。整理前，可以先保留共同字段：标题、链接、发布时间、来源类型和主要内容。论文作者与项目星标等特殊字段，再作为各自的补充信息。

    新闻列表 ─┐
论文列表 ─┼→ 统一条目结构 → 去重与日期筛选 → 主题分类 → 摘要与引用
项目列表 ─┘

    去重也不只是删除相同标题。同一项研究可能同时出现在新闻报道和论文页面；保留原始论文，再补充报道角度，通常比将它们写成两条无关新闻更清楚。日期还要分清抓取时间、发布时间和事件发生时间。

    生成节点的提示可以分别约定概述长度、重要性说明与来源位置。这样，读者不只看到“某项技术有进展”，还能知道这项进展是什么，以及应到哪里核对。

    5.2.3　预览时应该检查哪几层¶

    先看插件是否取得预期条目，再看筛选是否误删或保留过时内容，最后检查摘要是否改变了原意。若某个来源暂时没有结果，简报可以减少条目，但不应为了凑齐数量让模型补出新闻。

    这套检查过程同样适用于周报、论文追踪和竞品动态。任务换了，信息获取、规范化、筛选与生成之间的关系仍然可以复用。

    5.3　Dify：把多种个人助手能力放进一个应用¶

    Dify 案例把日常问答、文案处理、数据分析等能力放进统一入口。模型、知识库、插件和外部 MCP 服务，成为可以组合的应用资源。

    例如，用户问附近有哪些地点，助手需要调用地理信息工具；用户希望改写一段文字，则可能直接由模型处理。关键是把不同任务需要的能力描述清楚，让工具选择有依据。

    5.3.1　理解应用编排与运行管理¶

    本章还介绍模型配置、知识库接入和部署选择。将工具登记好之后，仍要检查调用记录：究竟使用了哪个服务，是否真的返回数据，以及最后回答有没有超出这些数据。

    云端服务与自建部署有不同的维护方式。自建能够控制更多组件，但如果仍调用外部模型或插件，相应数据依然可能被发送到外部接口。需要按实际链路判断数据流向。

    5.3.2　个人助手怎样区分不同请求¶

    一个入口覆盖多个任务时，可以先说明每项工具解决什么问题。改写文案主要处理用户提供的文本，查位置需要地理工具，分析文件则需要文件和计算能力。工具说明若互相重叠，模型就更难作出稳定选择。

    本章的插件与 MCP 配置可以分成连接测试和任务测试。连接测试确认服务能否被访问、是否能列出能力；任务测试再看助手是否在正确时机调用，参数与结果有没有被正确使用。

    例如，用户同时要求“找一个附近地点并帮我写邀请语”，查询结果应先提供实际地点，再成为邀请语中的素材。两项能力不能只是各自成功运行，还需要把结果正确传给后续处理。

    5.3.3　应用开发与运行管理为什么放在一起¶

    原文介绍的 LLMOps 可以理解为围绕模型应用的持续管理：保存配置、观察调用、分析反馈并更新版本。它关心的不只是能否生成，还包括变化以后是否仍按预期工作。

    同一问题换模型后，工具选择或格式可能变化。把运行记录和一组固定样例保留下来，就能比较变更的实际影响。平台提供集中入口，开发者仍要选择能够反映业务目标的观察点。

    5.4　FastGPT：让知识库与实时工具共同提供信息¶

    FastGPT 案例围绕一个投资信息助手展开。这里主要学习的是系统结构：一类问题依赖文档知识，另一类问题需要实时数据，两者应从不同路径获取。

    上传文档后，需要转换、分块、建立索引，再在提问时检索相关片段。行情或图表等即时信息，则由工具服务提供。模型负责组织材料，但应保留这些材料的来源和时间。

    5.4.1　为什么知识库和工具都需要¶

    一份介绍投资概念的文档，不会因为放进向量库就自动拥有最新价格；实时接口返回的数值，也不一定能够解释专业概念。把两种来源组合，才能分别处理这两类需要。

    这个案例不宜只看最后报告的排版。更重要的是检查：用户条件有没有被保留，检索片段是否相关，工具数据是否有效，以及结论能否由输入材料支持。漂亮的报告不是可靠性的替代品。

    5.4.2　知识导入到问答，哪些地方可以调试¶

    先导入一份范围明确的文档，确认标题、表格和段落是否被正确识别，再检查分块结果。若定义和适用条件被拆开，检索只取回定义时就可能丢失限制。

    接着使用已知答案的问题测试检索。例如，文档某节明确解释了一个术语，先确认对应片段能被取回，再观察生成回答。如果检索阶段已经失败，反复改写生成提示往往不是最直接的办法。

    实时工具则检查另一条路径：查询对象、时间与单位是否完整，结果是否真的对应用户的问题。把历史知识和即时数据分区交给模型，可以减少二者被混用的机会。

    5.4.3　多轮询问怎样更新用户条件¶

    原文案例还涉及收集用户需求。多轮输入可以逐步形成结构化条件，例如关注的主题、时间范围和期望报告形式。每次补充以后，应用需要更新记录，而不是只在不断增长的聊天里碰运气寻找。

    用户修改条件时，应明确哪些旧值已失效。这样，后续检索与工具查询才会使用同一份最新要求。最终报告中的每一项结论，也更容易追溯到用户输入或外部材料。

    5.5　n8n：让智能体进入已有业务流程¶

    n8n 的入口是事件与自动化。新邮件到达、定时任务触发或收到 Webhook，都可以启动一次处理；普通节点继续读写系统，AI Agent 节点则在其中选择工具并处理语言任务。

    原文的智能邮件助手分成知识准备和邮件处理两部分。

    5.5.1　先准备可检索的知识¶

    准备流程把文档切分并转换成嵌入向量，存入向量库。嵌入模型的作用是将文本表示成便于相似性比较的数值，而不是把文档训练进聊天模型。

    知识库随后作为一个工具供 Agent 使用。收到特定领域的问题时，它可以先检索，再根据相关材料拟定回复。

    5.5.2　再接入邮件主流程¶

    邮件触发器
  → AI Agent 读取主题和正文
  → 按需查询知识库或使用其他工具
  → 生成回复内容
  → 按配置的业务流程处理回复

    Chat Model、Memory 和 Tools 是 Agent 节点的不同配套组件。模型负责决策，记忆保留交互信息，工具连接实际能力。理解这种分工，比记住节点的界面布局更有帮助。

    原文演示使用的简易记忆与向量存储，不能直接等同于长期可靠的数据库。需要持续运行时，应核对持久化方式、重启后的状态、失败重试和重复事件处理。

    5.5.3　知识准备流程与邮件处理流程为什么分开¶

    知识准备只在资料新增或更新时运行：读取文本、分块、生成嵌入、写入索引。每封邮件到来都重新建立全部知识库，会重复消耗资源，也不利于稳定使用同一版本资料。

    邮件处理则从事件读取正文、发件人和会话标识，再交给 Agent。若需要引用已有知识，就查询准备好的索引；生成结果之后，再进入后续业务节点。

    资料更新事件 → 建立或更新知识索引

邮件到达事件 → 提取邮件字段 → 使用现有索引 → 生成处理结果

    当资料过时，应该更新知识库；当同一会话缺少前文，应该检查记忆与会话标识。这两类问题都表现为“回答不合适”，原因却不同。

    5.5.4　从单次演示到持续运行¶

    扩展邮件助手时，需要考虑同一事件是否会重复投递，以及失败后从哪里继续。可以保留消息标识与处理状态，区分尚未处理、处理中和已完成，避免重复执行后续动作。

    此外，知识索引、对话记忆和工作流执行记录各有用途。索引帮助找资料，记忆帮助接续交流，执行记录帮助排查节点。把它们放在不同存储中并不矛盾，关键是知道每一份数据由谁更新、会保存多久。

    5.6　怎样看待四种平台的取舍¶

    本章案例 主要观察点 更容易遇到的难题
    Coze 每日简报 插件获取与多源内容整理。 不同来源的数据结构和质量。
    Dify 个人助手 模型、插件与任务编排。 能力多了以后如何正确选择。
    FastGPT 知识助手 文档检索与外部工具结合。 检索结果能否支持回答。
    n8n 邮件助手 事件触发与业务系统连接。 状态保存、重试与重复处理。

    平台可以帮助快速验证想法。当应用需要更细的控制、复杂测试或定制协作时，我们还会回到代码。下一章就从这些需求出发，比较几种智能体开发框架。
