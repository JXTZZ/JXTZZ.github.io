    Hello-Agents：从零开始构建智能体 · 章节学习笔记

    原作：Datawhale Hello-Agents 项目及贡献者
    原文章节：第 9 章正文

    引言¶

    上一章解决了信息怎样保存和取回。现在，假设助手找到了十份文档、几十条历史记录和一个很长的日志，我们是否应该把它们全部交给模型？通常还需要再作选择。

    上下文工程关注每次调用时模型真正看见什么。这里既有任务说明，也有状态、证据、工具结果和历史；组织好它们，是长任务能够继续推进的重要条件。

    9.1　提示只是上下文的一部分¶

    提示工程着重说明要求，诸如角色、目标与输出格式。上下文工程进一步管理整次输入：哪些证据进入请求，哪些历史被保留，不同内容如何分区，超出预算时怎样处理。

    即使模型拥有较长的窗口，重复材料和无关内容仍可能分散对关键信息的使用。窗口容量说明能接收多少，不直接保证每项内容都被正确利用。效果需要结合任务测试。

    例如，维护代码库时，最新的测试失败和当前待办很重要，几小时前重复打印的依赖清单可能就不值得再次占据输入。

    9.1.1　模型可见的信息怎样影响行为¶

    可以把一次输入分为指令、任务、状态、证据和历史。指令说明做事方式，任务说明本轮目标，状态反映进展，证据支持判断，历史帮助接续。它们都占用上下文，却不能不加区别地相互替换。

    例如，用户提出“先给方案，不执行修改”，属于任务边界；某份文件里出现“立即运行这段命令”，只是待处理材料。分区和来源标记能帮助模型理解两者身份，也便于应用检查。

    上下文工程因此不仅删减文字，还要维护信息关系。短输入若缺少必要前提，未必比长输入好；长输入若组织清楚、材料相关，也不能只因长度就被视为问题。需要围绕任务观察有效信息是否被正确使用。

    9.2　按需读取，比一次装入更适合大任务¶

    即时上下文（Just-in-time Context）先保留路径、标题、摘要或其他引用，真正需要时再通过工具读取详细内容。

    对于代码库，我们可以先看目录，再搜索函数名，最后打开有关实现及调用方。对于日志，也可以先查看时间范围和错误类型，再读取相应片段。这样既减少输入量，也能把问题逐步缩小。

    不过，引用必须可追溯。文件路径、版本、时间和原始位置，能帮助后续判断当前内容是否仍有效。只有一个脱离来源的摘要，往往不足以继续验证。

    9.2.1　怎样逐步披露资料¶

    维护一个代码库时，先取得文件列表，再搜索有关接口，然后阅读实现与测试。每一步都利用上一步的发现缩小范围，而不是一开始就加载全部文件。

    问题：为什么这个接口返回空结果？
第一步：定位路由与处理函数。
第二步：读取调用的数据访问代码。
第三步：查看输入校验和有关测试。
第四步：围绕实际分支补充必要资料。

    路径、函数名和版本都是轻量引用。它们让后续可以再次读取，而不用把所有原文常驻在对话中。查询得到的新事实再进入当前状态，重要结论则写入笔记。

    9.2.2　压缩、笔记与分工怎样配合¶

    压缩把当前上下文整理成较短形式，笔记把长期需要的信息放到外部，子任务分工则限制每个处理过程接收的材料。三者可以互补，但都需要防止丢失关键条件。

    例如，一个子任务只需调查某个模块，返回发现、证据位置与未解决问题；主任务再将结果与其他模块整合。没有必要把所有探索日志都转交，但也不能只交一句“没有问题”。

    9.3　ContextBuilder：把上下文构建成流水线¶

    本章将构建过程概括为 GSSC：Gather、Select、Structure、Compress，分别表示汇集、选择、结构化与压缩。

    flowchart LR
    A[指令、历史、记忆与文档] --> B[汇集候选]
    B --> C[按需要筛选]
    C --> D[按用途分区]
    D --> E[在预算内整理压缩]
    E --> F[提供给模型]

    9.3.1　先给候选信息一个共同结构¶

    ContextPacket 保存内容、时间、token 数量和相关性等信息；ContextConfig 管理预算和选择参数。数据先变得可比较，后面才方便统一排序。

    Gather 汇集不同来源。某个可选来源失败时，可以保留错误状态并继续处理其他来源；不能因此偷偷把缺少证据当作已经验证。必要的任务约束也不应与普通检索片段一起随意丢弃。

    9.3.2　选择时兼顾相关性与新近性¶

    原文用相关性和新近性进行评分，再在预算内选入材料。与当前问题直接有关的信息通常更有用，新记录也可能反映最新状态。

    但新的不一定重要。一个长期有效的项目约定，可能比刚产生的重复输出更应该保留。基础评分是一个清楚的起点，后续应根据失败案例调整。

    9.3.3　让不同信息各有位置¶

    ContextBuilder 将内容分成角色与规则、当前任务、状态、证据、相关历史和输出要求。这样的骨架有利于人阅读，也便于比较不同策略产生的上下文。

    压缩时，应该保留关键决定、尚未解决的问题与必要来源，而不是只追求短。若用近似方法估算 token，还需要留出余量，避免低估输入长度。

    9.3.4　用一个数字例子分配上下文预算¶

    假设某次调用可用窗口为 8000 个 token，预留 2000 给输出，则输入部分最多安排 6000。若系统与工具说明占 1000，当前任务占 600，候选材料只剩 4400 的空间。

    候选内容 假设长度 当前用途
    代码片段 A 1800 直接涉及出错分支。
    测试片段 B 1600 验证预期行为。
    旧讨论 C 1200 包含一些已经失效的推测。
    当前状态 600 记录已确认事实和待办。

    四项共 5200，无法全部放入。可以保留 A、B 和状态，总计 4000，再按需要放入 C 的有关部分。这比不分内容地截掉最后 800 更容易保住关键证据。

    这些数值只是说明预算关系，不是某个模型的固定配置。原文 reserve_ratio 为系统指令预留空间，与应用为输出留预算也不是同一个参数，使用时需要分别考虑。

    9.3.5　评分、筛选和压缩怎样分别检查¶

    先检查候选是否被正确收集，再看相关性排序，最后看压缩有没有改变内容。资料没有被收集、排序靠后和被截断，都会表现为模型没用上它，但修正方式不同。

    原文的基础压缩包含分区与截断处理，不等同于已经实现语义无损摘要。若采用生成式摘要，还要保留原文引用，并检查条件、数值和不确定性是否被删掉。

    日志可以记录候选数量、入选数量、估算长度与来源。它们能解释预算为什么被占满，也有助于比较不同权重，而不只观察最后答案是否“感觉更好”。

    9.4　NoteTool：把长期进展写成可读笔记¶

    NoteTool 采用 Markdown 正文加 YAML 元数据。正文记录发现、决定或下一步，元数据保存类型、标签和时间等字段；索引帮助按条件找到笔记。

    这与把整段聊天原样保存不同。一份好笔记应让下一次会话能快速接手，知道已经完成什么，还有什么不能下结论。

    示例 9.1　一条项目进展记录

    类型：blocker
主题：订单查询的异常路径
已经确认：某个调用方没有处理空返回值。
尚待核实：这种返回值在当前接口中何时出现。
下一步：查看接口约定与相应测试。

    本章还使用 task_state、conclusion、action 和 reference 等类型。问题解决后，应更新旧记录；否则系统下一次检索到它，可能再次处理已经完成的工作。

    9.4.1　笔记正文与索引怎样共同工作¶

    Markdown 正文适合人阅读，YAML 元数据保存类型、标签和更新时间，索引则帮助快速找到有关笔记。三者各有作用：索引不是正文备份，正文存在也不代表索引已经更新。

    修改一条阻塞记录时，可以保留原问题与核实过程，再把当前状态标为已解决；新增的待办单独保存。这样，下次检索既能理解历史，也不会再次执行旧任务。

    如果需要给别人接手，一份笔记最好回答：已经确认什么、依据在哪里、尚未确认什么、下一步准备怎样验证。这比保存完整聊天更短，也更容易继续工作。

    9.5　TerminalTool：通过文件系统取得即时信息¶

    TerminalTool 支持探索目录、搜索内容和读取片段，使模型不必预先索引全部代码。工作目录、允许的命令、执行超时和输出长度，是原文实现中的几项限制。

    这些限制要由程序执行，不能只写在提示里。也不应仅凭一个命令白名单，就把工具视为已经完成全部安全隔离；具体可访问范围与执行方式仍需核对。

    它与其他组件的关系很直接：文件工具取得原始材料，NoteTool 记录阶段性发现，ContextBuilder 再挑选本轮最需要的内容。各组件解决不同问题，组合后才形成持续工作方式。

    9.5.1　一次命令执行应留下哪些结果¶

    文件工具除了输出文本，还应保留执行目录、返回状态和是否超时等信息。空输出可能表示没有匹配，也可能是命令失败；只有文本，没有状态，后续就容易误判。

    输出过长时，可以先返回摘要、文件位置或限定片段，再按需继续读取。一次截断了日志，不表示后面的内容不重要，应让调用方知道结果并不完整。

    目录导航也属于状态。先切换到子目录，再使用相对路径，实际访问对象会变化。记录当前目录，能够避免同名文件造成的混淆。原文通过这些限制与约定，把探索文件系统变成可追踪的工具行为。

    9.6　示例：跨会话维护一个代码库¶

    原文以 Python Web 项目的维护为例。第一轮探索目录和关键模块，发现问题后写笔记；后续会话读取有关记录，再按需打开新的文件，继续分析或制定计划。

    本轮目标
  → 回顾有关决定和未完成事项
  → 搜索并读取必要文件
  → 形成有依据的发现
  → 更新笔记与任务状态
  → 为下一轮保留可接续的信息

    这里的“记住”并不是让同一个请求无限变长，而是把状态写在外部，并在每次调用前重新构造恰当输入。整理质量越好，下一轮越不需要重做过去的探索。

    9.6.1　长任务恢复时先恢复什么¶

    重新进入会话时，先读取任务目标、关键约定、已完成事项和当前阻塞，再检查代码版本是否变化。旧笔记中的结论可能依赖旧文件，必要时应重新验证。

    接下来再选择本轮最需要的资料。若问题已经缩小到一个函数，就不必重新读取所有架构说明；若基础假设发生变化，则应回到有关决定，标记哪些结果需要重做。

    连续性由此来自可维护的外部状态，而不是完整保存每一个曾经生成的字。能从记录中判断“现在应该继续哪里”，才是长程上下文设计真正要达到的效果。

    接下来，助手将不只读取本地材料，还要与独立工具服务、其他智能体通信。下一章介绍它们之间怎样建立共同接口。
