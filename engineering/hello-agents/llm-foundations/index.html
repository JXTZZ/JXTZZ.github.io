    Hello-Agents：从零开始构建智能体 · 章节学习笔记

    原作：Datawhale Hello-Agents 项目及贡献者
    原文章节：第 3 章正文

    引言¶

    前两章把大语言模型放在智能体的决策位置。现在，我们不妨把这个组件拆开看看：一段文字怎样进入模型，模型怎样利用上下文，又怎样生成后面的内容？

    这一章从语言模型的基本任务讲起，逐步走到 Transformer、分词、提示和本地调用。了解这些机制，有助于判断一个问题该通过改提示解决，还是需要检索、工具或其他系统设计。

    3.1　语言模型在预测什么¶

    语言模型为文本序列建立概率模型。生成时，已经出现的内容构成条件，模型预测下一个词元的分布，再选择一个词元接到序列后面。

    若把序列写成 \(x_1,\ldots,x_T\)，可以表示为：

    \[ P(x_1,\ldots,x_T)=\prod_{t=1}^{T}P(x_t\mid x_1,\ldots,x_{t-1}). \]

    公式的意思并不复杂：整段文字的概率，可以分解为一步一步续写的条件概率。模型之间的重要区别，在于怎样表示前面的内容，以及怎样估计这些概率。

    N-gram 只看前面有限的几个单位，简单直接，却容易遗漏较远的关系。RNN 用隐藏状态连续处理输入，LSTM 又改进了信息保留方式。不过，循环结构需要顺序计算，长序列训练仍有困难。

    3.1.1　短窗口与隐藏状态各自保留了什么¶

    二元模型估计下一个词时，只考虑紧邻的前一个词；三元模型再多看一个位置。这样的统计可以从语料计数得到，却会随着组合增多迅速变得稀疏：完整长句可能从未出现过。

    词嵌入把离散词元表示成向量，使不同输入之间能够共享部分参数。神经网络由此不必为每一种短语都单独保存一条计数记录，而能学习在表示空间中利用相似模式。

    RNN 再用隐藏状态连续处理序列，形式上可以写成 \(h_t=f(h_{t-1},x_t)\)。状态试图压缩此前内容；LSTM 通过门控调整哪些信息保留、哪些被更新。这些机制改善了历史利用，却仍需沿时间顺序计算。

    这里可以区分两件事：能够接收很长的序列，不代表关键内容始终被可靠保留；能够表示历史，也不代表已经得到事实记忆。后面设计上下文和外部记忆时，这两个区别仍然重要。

    3.2　Transformer 怎样利用上下文¶

    Transformer 使用注意力（Attention）机制，让一个位置能够根据任务需要，从其他位置汇集信息。例如，理解代词指向谁，需要联系句子中相关的对象，而不是只看相邻几个字。

    3.2.1　查询、键和值¶

    自注意力把输入投影成查询（Query）、键（Key）和值（Value），常分别记为 \(Q\)、\(K\)、\(V\)。查询与键计算匹配程度，匹配程度决定怎样加权汇总值。

    \[ \operatorname{Attention}(Q,K,V)=\operatorname{softmax}\left(\frac{QK^{\mathsf T}}{\sqrt{d_k}}\right)V. \]

    可以先把它理解为：当前位置提出一个查询，比较其他位置与它的关联，再按权重取回信息。多头注意力并行执行多组投影，使模型能够从不同表示中组合信息。

    原文还逐步实现了位置编码、前馈网络、残差连接和归一化。位置表示帮助区分顺序，前馈网络继续变换每个位置的信息，残差与归一化帮助组织深层网络的计算。

    我们还可以用一组数观察加权汇总。假设两个位置经过缩放后的匹配分数分别为 2 和 0，Softmax 后权重大约是 0.88 和 0.12。如果对应的值简化成标量 20 和 10，输出大约是 0.88 × 20 + 0.12 × 10 = 18.8。

    实际网络使用高维向量，查询、键和值也由参数学习得到。这个小例子仅说明匹配分数怎样变成信息权重。权重反映计算中的关联，不应直接读成一个完整的人类解释。

    多头的作用也可以由此理解：不同投影让网络同时形成几组关联，再将它们组合。不是事先规定某个头一定负责语法、另一个头一定负责事实，而是训练让参数形成有用分工。

    3.2.2　从编码器—解码器到 Decoder-Only¶

    原始 Transformer 为翻译任务使用编码器与解码器。编码器处理输入，解码器结合输入表示生成输出。

    许多生成式语言模型采用 Decoder-Only 架构，将任务统一成在已有序列后继续生成。训练时使用因果掩码，避免某个位置看到它本来要预测的后续答案；使用时则逐个生成新词元。

    这里的并行能力主要帮助已知序列上的训练和部分推理计算。生成多个新词元时，普通自回归解码仍要依次推进，不能理解为整篇回答同时产生。

    3.2.3　注意力之外的模块为什么不能省略¶

    位置编码或其他位置表示帮助区分“谁在谁前面”。只比较词元内容，无法充分表达语序；将位置信息加入表示后，模型才有机会学习顺序关系。

    前馈网络（FFN）对各位置进一步作非线性变换；残差连接为信息与梯度提供较直接的通路；层归一化则调整中间表示的尺度。注意力负责交流信息，这些模块负责继续加工并组织深层计算。

    原文采用逐个补全模块的方式展示 Transformer。阅读代码时，可以先记录每一层的张量形状，再看计算。批次、序列长度、隐藏维度和头数一旦混淆，公式即使写对，代码也可能无法正确组合。

    3.2.4　因果掩码与自回归生成¶

    训练时已经知道整段文本，但预测某个词元时不能借看后文。因果掩码把未来位置排除在可用范围之外，让训练问题与实际续写相匹配。

    推理时，模型读取现有前缀，产生一个新词元，再把它接回输入继续生成。因此，训练一个已知序列可以利用并行计算，而未知的后续通常仍要逐步产生。理解这一区别，也就容易理解为什么长输出会带来额外延迟。

    生成还需要结束条件，例如遇到终止标记或达到长度限制。被长度限制截断的答案，不应与自然完成的答案混为一谈。

    3.3　文本怎样变成词元¶

    模型不能直接处理屏幕上的字符，需要先通过分词器（Tokenizer）把文本转换成 token ID，再查找相应的向量表示。

    按完整单词切分容易遇到词表过大和新词问题；按字符切分又可能把序列拉得很长。子词方法在二者之间折中，将常见片段作为单位，再组合较少见的词。原文用代码演示 BPE 逐步合并常见片段，还介绍了 WordPiece 与分词工具 SentencePiece。

    一个 token 不固定等于一个汉字或一个英文单词。同一段文本，使用不同分词器，长度也可能不同。因此，估算上下文容量和调用成本时，应使用对应模型的分词方式。

    3.3.1　BPE 的合并过程在改变什么¶

    BPE 从较小单位出发，统计相邻片段，逐步合并常见组合。以一个简化词表为例，test 与 tests 共享一段前缀，若这段组合频繁出现，就可能被合并成较大的单位。

    初始表示：t e s t / t e s t s
某轮合并：te s t / te s t s
继续合并：tes t / tes t s
后续表示：test / test s

    这是合并思路的示意，不是某个现成模型的实际分词结果。训练分词器时要考虑整份语料的频率；使用分词器时则按已经确定的词表与规则编码，通常不会在每次聊天时重新学习合并规则。

    分词器还定义特殊标记与对话边界。模型权重、词表和聊天模板需要匹配；随意换一个分词器，即使文本相同，也可能改变输入 ID 的含义。

    3.4　怎样更清楚地向模型提出要求¶

    提示工程（Prompt Engineering）首先是把任务说明白：需要处理什么输入、遵守哪些条件、输出什么内容，以及缺少信息时该怎样处理。

    零样本提示只给指令；单样本与少样本提示再提供一个或多个示例。示例不仅展示答案，还能说明格式与边界。例如，分类任务最好展示不同类别，而不只展示一种情况。

    3.4.1　生成参数改变的是采样方式¶

    Temperature 调整概率分布的集中程度，Top-k 和 Top-p 则限制候选范围。较低温度通常让输出更集中，但不能把错误知识变成正确知识，也不保证整个系统每次结果完全一致。

    我们可以用这些参数控制生成风格，再通过任务评测选择配置。若需要准确的票价或计算结果，仍应调用对应工具，而不是期待调低温度解决事实问题。

    3.4.2　指令调优与上下文示例¶

    指令调优通过训练改变参数，让模型更好地响应任务要求；在提示里放几个示例，则只是改变这次输入。两者都能影响行为，发生的位置却不同。

    这个区别在后面会反复出现：上下文帮助模型使用当前信息，训练则改变它通常怎样处理问题。

    3.4.3　把一项模糊要求写成可执行提示¶

    “总结一下这份材料”没有说明读者、长度和依据。可以改为：面向首次接触该主题的读者，先解释要解决的问题，再写主要方法与限制；只依据所给材料，缺少的信息单独说明；保留来源位置。

    这种提示给出了任务、背景、约束和交付格式。它没有把所有中间步骤写死，但已经让结果更容易检查。少样本示例可以进一步展示什么叫合格段落，尤其是容易混淆的边界。

    任务：需要完成什么。
材料：这次允许使用哪些信息。
约束：必须保留或不能自行补充什么。
输出：标题、字段、长度与表达方式。
检查：哪些条件满足以后才算完成。

    对于复杂问题，可以要求模型按若干明确子任务处理，并检查中间结果。关键是提供可核对的结构与证据，不是让它输出越来越长的分析。长文本同样可能掩盖错误。

    3.5　示例：在本地加载一个模型¶

    原文用 Transformers 演示本地调用，关键组件是 AutoTokenizer 和 AutoModelForCausalLM：前者加载分词与对话模板，后者加载生成模型。

    示例 3.1　沿着数据走一遍

    选择模型与匹配的分词器
  → 按该模型要求组织对话
  → 转成 token ID
  → 模型生成后续 ID
  → 将生成部分解码成文本

    理解流程比记住示例中的具体型号更重要。不同模型可能要求不同的对话模板，显存需求还受到精度、上下文长度和缓存等因素影响。能加载权重，不代表已有适合交互使用的速度。

    选型时应共同考察任务表现、工具调用能力、延迟、费用、部署条件和使用许可。本章列举的模型是原文写作时的案例，不宜直接当作今天的性能排名。

    3.5.1　加载、生成与解码应当分别观察¶

    本地调用先加载权重与分词器，再按模型的聊天模板组织消息。模板中的角色边界会影响模型怎样理解用户输入，不能简单把所有句子直接拼接。

    生成结果有时包含输入前缀。展示时需要确认返回的是整段序列，还是仅新增部分；否则可能把用户问题重复显示成答案。还应检查结束原因与实际生成长度，区分自然结束和上限截断。

    速度也不只有一个指标。加载耗时、首次响应延迟与持续生成速度分别对应不同阶段；较长输入还会增加前缀处理和缓存开销。选模型时，可以使用自己的典型输入分别观察这些部分。

    对于智能体，最终还需要检查工具指令能否稳定生成。一个在闲聊中表现良好的模型，不一定在参数构造和多轮错误恢复中同样合适。这也是后面需要专门评估工具调用的原因。

    3.6　规模扩大以后，哪些问题仍然存在¶

    缩放法则研究参数量、数据量、计算量与训练损失之间的经验关系。它帮助研究者分配预算，但并不是“参数越多，所有任务就越可靠”的保证。数据规模与质量，以及资源之间的配比，同样重要。

    模型还可能产生事实错误，或没有忠实反映给定材料。训练数据中的矛盾、知识过时和推理失误都可能影响输出。流畅的语言，使这些错误有时更难被察觉。

    构建智能体时，我们因此不能只安排生成，还要安排信息获取与检查。下一章将用三种经典范式说明：怎样把模型的一次回答，组织成可以与工具和反馈配合的过程。
