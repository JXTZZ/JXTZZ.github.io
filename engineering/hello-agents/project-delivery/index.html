    Hello-Agents：从零开始构建智能体 · 章节学习笔记

    原作：Datawhale Hello-Agents 项目及贡献者
    原文章节：第 16 章正文

    引言¶

    前面已经有能规划行程、整理资料和参与游戏对话的系统。现在，假设另一位同学拿到代码，他能否知道怎样配置、怎样启动、怎样判断运行结果是否正常？

    这一章把注意力转向完整交付。这里保留原文关于选题、开发、测试、文档和协作的设计思路，省略具体毕业设计的实现与作业提交要求。

    16.1　完整项目从一个具体问题开始¶

    项目的价值首先来自解决了什么问题。比起“做一个什么都会的多智能体助手”，先说明用户、输入和交付物，更容易判断范围是否合适。

    原文列举生产力、学习、创作、分析和生活服务等方向。它们的共同点是可以围绕实际使用过程组织，而不是为了展示所有技术而加入组件。

    例如，代码审查助手可以先限定一种语言、一个仓库和几类问题，再逐步扩展。静态分析本身已经能发现一部分逻辑问题，大模型的作用应建立在已有工具之上，而不是假定过去工具只能检查语法。

    16.1.1　把想法写成输入、处理和交付物¶

    “帮助学习”或“自动做研究”范围很大。可以先限定用户是谁、当前在哪一步遇到困难、能够提供什么资料，以及最后需要什么形式的结果。

    例如，文档助手可以先处理一类文件，回答带来源的具体问题；代码审查助手可以先检查一种语言中的若干问题。这样，系统失败时容易知道是否超出范围，评价时也有明确对象。

    范围限定还包括资源。可用模型、外部服务、运行时间和数据访问条件，都会影响方案。先把这些约束说清楚，能减少开发到一半才发现关键条件不具备的情况。

    16.2　先完成一条能够检查的路径¶

    可以把最小流程写成：

    接收输入
  → 获取必要信息
  → 完成核心处理
  → 验证结果
  → 交付产物，并说明尚未完成之处

    这条路径需要真正连通。只有多个角色各自能够回复，还不能证明它们共同完成了任务；只有一份漂亮报告，也无法说明里面的信息经过检查。

    16.2.1　按需要选组件¶

    遇到的问题 可以考虑的组件
    下一步依赖外部结果 ReAct 或其他工具循环。
    需要清楚的多步安排 计划与状态管理。
    要引用私有文档 RAG 与来源记录。
    要跨会话继续工作 持久化记忆和结构化笔记。
    要接入独立服务 合适的协议或工具适配。
    要知道修改是否有效 任务集、评价指标与失败记录。

    这些能力不必全部出现在一个项目里。系统越简单，越容易看出新增组件是否解决了实际困难。

    16.2.2　先建立最小基线，再解释新增能力¶

    最小基线可以是一次模型请求、固定工作流或已有规则工具。先记录它在代表性任务上怎样表现，再加入检索、记忆或多角色，观察具体改善。

    这样能回答“为什么需要这个组件”。若增加多个角色后，只是费用变高而问题发现没有改善，可能应该先调整职责或保留更简单结构；若检索明显补足知识缺口，则有清楚理由继续完善。

    16.2.3　架构图应该画出数据与失败路径¶

    画一个模型连接多个工具还不够。需要说明输入存在哪里，工具结果怎样回到决策，最终产物怎样交付，以及失败后如何继续。

    输入与约束 → 决策组件 → 工具或资料
                 ↑          │
                 └─ 状态与结果
                       ↓
                 验证与交付

    这张简化图可以落实为目录、接口和测试。组件之间一旦存在未说明的数据转换，往往也是后面需要重点调试的位置。

    16.3　把实现组织成可以接手的结构¶

    原文通过 Notebook 或脚本展示完整流程，另用依赖文件和 README 说明运行方式。较复杂项目还可以将 Agent、工具、服务和测试分别组织。

    Notebook 适合把解释、操作和结果放在一起，但要注意隐藏状态。一次从头执行，应当能够重建必要变量，不能依赖作者先前单独运行过某个单元。

    配置则应与核心实现分开。外部服务地址、模型名称和凭证都可能变化；提供配置示例，比把个人环境写死在代码里更利于复现。

    16.3.1　目录怎样帮助别人找到修改位置¶

    一种可理解的组织方式，是把入口、配置、Agent、工具、测试与小样例分开。目录名字不必完全统一，职责却应容易识别。

    project/
  ├─ README.md
  ├─ requirements.txt
  ├─ config.example
  ├─ main.py
  ├─ agents/
  ├─ tools/
  ├─ tests/
  └─ examples/

    这是组织思路的示意，不是毕业设计的强制格式。小项目可以更简单；较大项目则可以进一步拆服务和数据模型。重点是修改模型配置时不必到工具内部找，增加工具时也不必重写入口。

    16.3.2　Notebook 还需要解释运行顺序¶

    Notebook 把说明和操作放在一起，适合教学，但单元之间可能存在隐藏依赖。最好能够从头顺序运行，并说明哪些步骤创建索引、启动服务或消耗外部调用。

    导出的结果也应与当前代码对应。旧运行留下的输出，如果来自不同配置，会让读者误以为已经复现。保存少量可解释结果，比保留大量无法追溯的日志更有帮助。

    16.4　README 应当回答读者接下来的问题¶

    一份有用的 README 不只是项目宣传。读者首先需要知道它能完成什么，接着才是需要准备什么、怎样运行，以及正常情况下会看到什么。

    示例 16.1　一次顺畅的接手过程

    读懂项目范围
  → 安装与版本匹配的依赖
  → 填写配置
  → 用小样例运行
  → 对照预期产物检查
  → 了解限制，再尝试自己的数据

    如果某项功能仍在规划中，应与已实现部分分开。示例输出也要说明来自真实运行、固定测试还是展示数据，避免让下一位读者把演示误当作保证。

    16.4.1　依赖与外部资源也属于交付内容¶

    依赖文件需要能支持项目，而不是随意列出几个库。若运行还需要数据库、Node 服务或特定模型文件，应一并说明对应关系。

    较大的模型、数据与视频可以放在合适的外部位置，仓库保留小样例和获取说明。资源能否访问、是否有必要授权，会直接影响别人能否复现。

    16.4.2　依赖声明怎样支持复现¶

    依赖文件说明项目需要哪些库，配置示例说明这些库连接到什么服务，运行说明再给出执行顺序。三者共同工作，仅列出库名不足以保证另一个环境能够启动。

    对容易变化的接口，可以记录已验证版本与使用条件。并不要求把作者机器上的所有包原样复制，而是尽量明确真正影响这个项目的依赖。

    若还需要模型、数据库或外部资源，应说明获取与初始化方式。小样例能帮助读者先确认链路，再换成自己的数据，降低第一次运行时同时排查很多问题的负担。

    16.4.3　示例输出应该帮助读者判断什么¶

    一份示例最好同时提供输入、关键配置与预期产物。这样，读者看到不同结果时，可以判断是允许的语言差异，还是关键条件没有满足。

    例如，研究助手允许段落表达不同，但引用应可访问并支持结论；代码审查报告允许排序不同，但应指出具体触发条件。预期结果因此不总是固定文本，也可以是一组可检查性质。

    16.5　测试一条真实使用路径¶

    先检查正常输入，再检查缺少字段、服务超时、错误凭证、空结果等边界。对于会重复执行的流程，还要留意重复请求是否改变持久状态。

    模型、工具和完整应用最好分层验证。工具测试确认接口行为，固定资料测试有助于复现，端到端任务则检查最后目标。外部服务变化造成的失败，也应与本地逻辑问题分开记录。

    评价标准来自项目目标。代码审查关注问题能否复现，研究助手关注来源是否支持判断，旅行助手关注条件是否满足。只使用一个“回答看起来不错”的分数，很难指导后续修改。

    16.5.1　把单项测试与任务评价连接起来¶

    单项测试检查确定行为，例如参数校验、费用求和或状态转换；任务评价则检查多个组件连接以后能否完成用户目标。前者通过，不等于后者自动成功。

    可以用固定工具响应检查控制流程，再用实际服务观察运行条件。涉及模型生成时，保留多次结果和失败样例，避免只挑最成功的一次作为全部证据。

    16.5.2　异常处理也是产品行为¶

    缺少配置时，应指出需要补什么；外部服务失败时，应保留已经完成的工作，并说明能否继续。合理结束和诚实报告，都是完整应用的一部分。

    若流程会写入文件或保存状态，重试还要避免重复生成混乱数据。可以围绕同一任务标识管理中间结果，明确哪些阶段可复用、哪些需要重新执行。

    这种设计让用户能够理解系统当前处境，也使后续维护者更容易定位问题，而不是只看到一个没有说明的失败提示。

    16.6　开源协作是交付后的继续工作¶

    原文介绍 Fork、分支、提交和 Pull Request。这些操作背后的目的，是让修改能够被独立查看、讨论和验证。

    一份清楚的变更说明，应指出解决了什么问题、行为有什么变化、运行过哪些检查，以及仍有哪些限制。收到评审后，再用代码和验证结果回应具体问题。

    16.6.1　评审时怎样提供可核对的信息¶

    提交修改时，可以围绕问题、最终行为、验证方式和剩余限制组织说明。评审者首先需要理解这项变更为什么存在，再看实现是否合适。

    讨论意见时，说明修改对应了哪一个问题，并提供相关验证结果。若没有采用某项建议，也应解释实际约束。这样，讨论能够围绕具体取舍继续，而不只停留在风格偏好。

    16.6.2　从演示走向持续维护¶

    演示关心第一次能否运行，维护还要考虑下一次数据更新、模型替换和依赖变化。把关键约定、版本与任务样例保存下来，能让之后的修改仍有比较依据。

    项目不必一次覆盖所有能力。先交付一条清楚、可验证的使用路径，再根据真实反馈逐步扩展，既能展示所学，也更容易积累能够复用的工程经验。
