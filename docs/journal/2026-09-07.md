# 论文速记与 WSL 网络配置

今天的阅读围绕一个问题展开：模型在机器人任务上取得高成功率，究竟说明它学会了什么？另外，也记录一下 Windows 已能使用代理、WSL 中却仍然无法克隆仓库的处理过程。

## DroneCATS：理解画面之后，能否持续执行动作协议

[DroneCATS](https://arxiv.org/abs/2609.01404)把多模态大语言模型放进无人机控制循环，直接在提示词中说明动作空间，不微调模型，也不预先提供固定的函数调用格式。评估覆盖接近目标、跟踪、搜索和多机指挥。

有意思的是，接近目标与正确结束任务未必同步。模型可能已经飞进成功范围，却因为过早宣布到达，或始终没有发出结束动作而失败。看懂场景、选择动作、遵守交互协议，是需要分别检查的能力。

这项工作让我想继续比较：任务失败时，问题出在空间判断，还是出在动作选择与终止条件？只有把失败拆开，才能判断是否需要更强的视觉模型，或是更明确的执行接口。

## MINERVA：高成功率能说明泛化能力吗

[MINERVA](https://arxiv.org/abs/2609.03715)用小型视觉动作策略考察 LIBERO 到底需要多大的模型。论文报告，一个 **0.54M 参数**的策略，在四套标准任务、共 2,000 次执行中取得 95.1% 的平均成功率。

作者还改变了任务 ID 的对应关系，并在 LIBERO-Plus 的扰动条件下测试。前者使表现接近随机，后者的成功率降至 46%～56%。这些实验提醒我们，固定任务集上的高分，与适应场景变化的能力，需要分开看。

任务 ID 打乱后表现下降，直接说明策略依赖这些标识来选择行为；单靠这一项实验，还不能解释所有模型的失败。结合光照、布局等扰动测试，才能更具体地判断策略记住了什么、又在哪些变化下失效。

## WSL 无法正常执行 `git clone` { #wsl-git-clone }

Windows 已连接代理，但 WSL 中的 `git clone` 仍无法访问远程仓库。一个可能的原因是，Windows 的代理配置没有被 WSL 正确使用。下面记录的是这次采用的配置方式；由于原记录没有保留完整错误输出，不能据此把所有克隆失败都归因于代理。

### 先确认网络模式

以下方法适用于支持镜像网络的 WSL 2 环境。微软文档给出的系统条件是 **Windows 11 22H2 或更高版本**；旧系统或不支持相应选项的 WSL，需要采用其他网络配置方式。镜像网络允许 Linux 通过 `127.0.0.1` 连接 Windows 上的服务，自动代理则用于导入 Windows 的 HTTP 代理信息。见[微软 WSL 网络说明](https://learn.microsoft.com/en-us/windows/wsl/networking)。

代理软件中的“允许局域网连接”是否需要开启，取决于实际连接方式。若通过宿主机局域网地址访问代理，需要检查监听地址；若在镜像网络下使用本机回环地址，则应先检查这一连接是否可用。

### 修改 `.wslconfig`

在 Windows 的 PowerShell 中打开用户目录下的配置文件：

```powershell
notepad "$env:USERPROFILE\.wslconfig"
```

若文件不存在，可以新建；若已有 `[wsl2]` 段落，将以下选项合并进去：

```ini
[wsl2]
networkingMode=mirrored
dnsTunneling=true
autoProxy=true
```

三个选项分别控制镜像网络、DNS 隧道和自动代理。它们作用不同；自动导入代理地址之后，仍需要确保 WSL 能连接到该地址。

保存 WSL 中的工作，再回到 Windows PowerShell 执行：

```powershell
wsl --shutdown
```

重新打开 WSL 后，配置才会生效。

### 怎样确认连接恢复

可以先在 WSL 中查询一个自己有权访问的仓库，避免每次排查都下载完整代码：

```bash
git ls-remote https://github.com/git/git.git HEAD
```

若返回提交标识与 `HEAD` 引用，说明这次 Git 远程查询成功；私有仓库的访问权限仍需另行确认。若仍失败，应保留完整报错，继续区分代理连接、DNS、地址重写和认证问题。[后来的 Git 地址重写排查](2026-10-15.md)就是另一种看起来相似、原因却不同的情况。

这份配置会持续保存。代理地址、端口或网络模式改变后，再检查相应设置即可。
