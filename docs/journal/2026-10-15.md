# GitHub 克隆失败排查：从认证报错定位到地址重写

今天在 Windows PowerShell 中克隆一个私有仓库的指定分支，遇到了“仓库不存在”和“认证失败”的提示。检查后发现，Git 的全局配置把 GitHub 地址改写到了第三方代理。临时绕过这条规则后，已有凭据就能完成分支查询与克隆。

这次排查值得记下的，是报错中的访问地址与输入地址并不相同。沿着这一差异检查，比直接更换凭据更容易缩小问题范围。

下文的组织名、仓库名、分支名、代理域名、路径和提交标识均使用示例值。复制命令前，应替换为自己的实际配置。

## 先比较输入地址与报错地址

最初执行：

```powershell
git clone -b example-branch --single-branch https://github.com/example-org/example-repo.git
```

返回：

```text
remote: Repository not found.
fatal: Authentication failed for 'https://git-proxy.example/https://github.com/example-org/example-repo.git/'
```

命令写的是 `github.com`，错误中却出现了 `git-proxy.example`。因此，下一步应先检查地址有没有被 Git 配置改写。

`Repository not found` 本身也可能与地址或访问权限有关，不能单靠这一行判断凭据失效。见 [GitHub 克隆错误说明](https://docs.github.com/en/repositories/creating-and-managing-repositories/troubleshooting-cloning-errors)。

## 找到全局 insteadOf 规则

查看地址重写规则及其配置来源：

```powershell
git config --show-origin --get-regexp '^url\..*\.insteadof$'
```

这次定位到用户目录下的全局 `.gitconfig`，其中有类似设置：

```ini
[url "https://git-proxy.example/https://github.com/"]
    insteadOf = https://github.com/
```

`insteadOf` 替换匹配到的 URL 前缀，于是 GitHub 仓库地址变成了：

```text
https://git-proxy.example/https://github.com/example-org/example-repo.git
```

这解释了为什么输入官方地址，实际仍然访问代理。但它还不能解释代理内部为何返回认证错误；当时没有服务端日志，只能继续通过改变访问路径来验证。

## 临时绕过重写，先查询目标分支

本机已有 Git Credential Manager 管理的 GitHub 凭据。先增加一条只对本次命令生效、匹配前缀更长的规则，再查询远程分支：

```powershell
git -c 'url.https://github.com/example-org/.insteadOf=https://github.com/example-org/' ls-remote --exit-code --heads https://github.com/example-org/example-repo.git example-branch
```

返回形式如下：

```text
<commit-sha>    refs/heads/example-branch
```

这说明在当时的运行环境与凭据下，能够访问仓库，目标分支也存在。随后完整克隆成功，进一步支持访问路径与这次失败有关的判断。

如果排查时更换了终端、代理或工具的执行环境，也应记录这些变化。不同环境中的连接或 Schannel 错误，需要分别确认原因，不能直接视为最初认证失败的证据。

## 克隆并保存仓库内的规则

以 `D:\Workspace` 为示例工作目录：

```powershell
cd D:\Workspace
git -c 'url.https://github.com/example-org/.insteadOf=https://github.com/example-org/' clone --config 'url.https://github.com/example-org/.insteadOf=https://github.com/example-org/' -b example-branch --single-branch https://github.com/example-org/example-repo.git
```

命令中两处配置分别用于当前操作与后续访问：

- `git -c ...` 为本次命令设置规则，使初次克隆保留 GitHub 地址。
- `clone --config ...` 将规则写入新仓库的 `.git/config`，供后续操作使用。该选项在仓库初始化后、抓取历史前写入，见 [Git clone 文档](https://git-scm.com/docs/git-clone)。
- `-b example-branch --single-branch` 检出指定分支，并限定常规抓取范围。

保存下来的规则是：

```ini
[url "https://github.com/example-org/"]
    insteadOf = https://github.com/example-org/
```

它把地址替换为自身，因此保留原地址。关键在于 `https://github.com/example-org/` 比全局规则中的 `https://github.com/` 更长。多个 `insteadOf` 规则同时匹配时，Git 使用匹配前缀最长的一条，详见 [Git 配置说明](https://git-scm.com/docs/git-config#Documentation/git-config.txt-urlltbasegtinsteadOf)。仅用“本地配置优先”来解释，容易遗漏这个条件。

如果仓库已经存在，可以在仓库内设置同样的规则：

```powershell
cd D:\Workspace\example-repo
git config --local 'url.https://github.com/example-org/.insteadOf' 'https://github.com/example-org/'
```

这次克隆命令已经保存了配置，无需再重复设置。

## 分别验证本地状态与远程访问

克隆完成后执行：

```powershell
cd D:\Workspace\example-repo
git status --short --branch
git rev-parse --short HEAD
git ls-remote --get-url origin
```

输出形式为：

```text
## example-branch...origin/example-branch
<short-sha>
https://github.com/example-org/example-repo.git
```

这些结果确认了当前分支、提交和工作区状态，也确认解析后的远程地址仍是 GitHub 地址。其中 `git ls-remote --get-url origin` 只展开地址，不发起网络请求。真正的远程访问，已由前面的分支查询和完整克隆验证。

## 其他仓库是否还会遇到同样的问题

这次修复保存在目标仓库内，全局规则仍然存在。其他新克隆的 GitHub 仓库还可能经过同一个代理。

如果今后决定不再使用该代理，可以先查看全局规则：

```powershell
git config --global --get-regexp '^url\..*\.insteadof$'
```

核对实际配置后，再删除对应的一条值：

```powershell
git config --global --fixed-value --unset-all 'url.https://git-proxy.example/https://github.com/.insteadOf' 'https://github.com/'
```

这是另一种处理方式，本次没有执行。它会影响使用这条全局规则的其他仓库，示例代理域名也必须换成实际值。

以后遇到类似错误，我会先对照输入与报错中的主机，再查看配置来源。找到可疑规则后，用一次临时配置和只读查询验证判断，最后才决定将修改保存在哪个范围。
