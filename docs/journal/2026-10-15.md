# GitHub 克隆失败排查：从认证报错定位到地址重写

今天在 Windows 的 PowerShell 中克隆一个私有仓库的指定开发分支时，遇到了“仓库不存在”和“认证失败”的提示。最初容易怀疑账号权限，但检查后发现，**全局 Git 配置把 GitHub 地址重写成了第三方代理地址**。绕过重写后，本机已有凭据即可完成分支查询与克隆。

下面按“如何发现 → 为什么出现 → 怎样修复 → 如何验证”记录排查过程。

> 本文中的组织名、仓库名、分支名、代理域名、本机路径和提交标识均已替换为示例值。`example-org`、`example-repo`、`example-branch` 与 `git-proxy.example` 仅用于说明，命令使用前需替换为自己的实际配置；密码、令牌和其他认证信息不应写入日志。

## 问题是怎么发现的

最初执行的命令是：

```powershell
git clone -b example-branch --single-branch https://github.com/example-org/example-repo.git
```

返回错误：

```text
remote: Repository not found.
fatal: Authentication failed for 'https://git-proxy.example/https://github.com/example-org/example-repo.git/'
```

关键线索藏在报错的 URL 中：**输入的是 `github.com`，实际访问的却是第三方代理域名（此处记作 `git-proxy.example`）**。这意味着需要先检查 Git 是否改写了地址，再判断仓库权限与认证状态。单看 `Repository not found` 无法区分仓库地址错误、权限不足等情况；[GitHub 官方排查文档](https://docs.github.com/en/repositories/creating-and-managing-repositories/troubleshooting-cloning-errors)也要求检查仓库地址与访问权限。

## 为什么会出现这个问题

排查定位到用户目录下的全局配置文件 `.gitconfig`，其中存在以下规则：

```ini
[url "https://git-proxy.example/https://github.com/"]
    insteadOf = https://github.com/
```

`insteadOf` 会替换匹配到的 URL 前缀，因此原始克隆地址被转换为：

```text
https://git-proxy.example/https://github.com/example-org/example-repo.git
```

所以，即使命令明确写了 GitHub 官方地址，Git 仍会通过第三方代理访问。**已确认的原因是全局重写改变了访问路径，绕过该路径后访问成功**；由于没有代理服务端日志，尚不能确定代理内部为什么返回认证错误。

以后遇到同类现象，可以先用下面的命令查看重写规则及其来源：

```powershell
git config --show-origin --get-regexp '^url\..*\.insteadof$'
```

### 用分支查询验证判断

本机已有 Git Credential Manager 管理的 GitHub 凭据。为了判断问题是否出在代理访问路径，排查时临时绕过全局重写，先执行只读的分支查询：

```powershell
git -c 'url.https://github.com/example-org/.insteadOf=https://github.com/example-org/' ls-remote --exit-code --heads https://github.com/example-org/example-repo.git example-branch
```

成功返回分支引用，脱敏后的输出形式如下：

```text
<commit-sha>    refs/heads/example-branch
```

这说明当时的本机环境可以访问仓库，目标分支也确实存在。随后完整克隆成功，进一步支持了“绕过代理重写即可恢复访问”的判断。

排查工具本身还曾在执行沙箱中遇到本地代理连接失败和 Windows Schannel 凭据错误，改在沙箱外执行后访问成功。这些是排查环境中的额外现象，应与最初克隆命令的失败原因分开记录。

## 问题是怎么解决的

### 克隆时临时绕过重写，并保存后续配置

本次在本地工作目录下执行以下命令，完成了目标分支的克隆。以下以 `D:\Workspace` 为示例目录：

```powershell
cd D:\Workspace
git -c 'url.https://github.com/example-org/.insteadOf=https://github.com/example-org/' clone --config 'url.https://github.com/example-org/.insteadOf=https://github.com/example-org/' -b example-branch --single-branch https://github.com/example-org/example-repo.git
```

参数含义：

- `git -c ...`：为本次命令增加更具体的重写规则，使克隆保留 GitHub 原始地址。
- `clone --config ...`：把规则保存到新仓库的 `.git/config`，用于后续访问；该选项会在新仓库初始化后、抓取历史前写入配置，见 [Git clone 文档](https://git-scm.com/docs/git-clone)。
- `-b example-branch --single-branch`：检出指定分支，并将常规抓取范围限定为该分支。

新仓库中的规则为：

```ini
[url "https://github.com/example-org/"]
    insteadOf = https://github.com/example-org/
```

[Git config 文档](https://git-scm.com/docs/git-config#Documentation/git-config.txt-urlltbasegtinsteadOf)规定：多个 `insteadOf` 规则同时匹配时，采用匹配前缀最长的一条。这里的 `https://github.com/example-org/` 比全局规则的 `https://github.com/` 更长，而且替换前后相同，因此保留了官方地址。它生效的关键是**更长的前缀匹配**，不能仅理解为“本地配置优先于全局配置”。

### 已有仓库的等效配置

如果仓库已经存在，可以在仓库内执行：

```powershell
cd D:\Workspace\example-repo
git config --local 'url.https://github.com/example-org/.insteadOf' 'https://github.com/example-org/'
```

本次克隆已保存该配置，无需重复执行。

## 修复后是怎么验证的

以下以示例路径 `D:\Workspace\example-repo` 说明验证步骤。

执行：

```powershell
cd D:\Workspace\example-repo
git status --short --branch
git rev-parse --short HEAD
git ls-remote --get-url origin
```

结果形式如下（提交标识与分支名已替换）：

```text
## example-branch...origin/example-branch
<short-sha>
https://github.com/example-org/example-repo.git
```

验证结果表明：克隆成功，当前处于目标分支，工作区干净，解析后的远端地址为 GitHub 官方地址。

其中 `git ls-remote --get-url origin` 仅检查地址解析，不发起网络请求；实际网络访问已通过前面的分支查询和完整克隆验证。

## 后续怎样避免重复遇到

**本次未修改全局配置。** 修复通过目标仓库的本地配置生效，因此其他新克隆的 GitHub 仓库仍可能受到原有全局重写影响。

如果今后希望所有 GitHub 仓库都直接访问官方地址，可以先查看规则：

```powershell
git config --global --get-regexp '^url\..*\.insteadof$'
```

确认不再需要该第三方代理后，可删除这条特定的全局规则：

```powershell
git config --global --fixed-value --unset-all 'url.https://git-proxy.example/https://github.com/.insteadOf' 'https://github.com/'
```

以上删除命令是可选方案，本次没有执行。使用时需将示例代理域名替换为配置中的实际值；它会影响使用这条全局规则的其他 GitHub 仓库。

## 今日结论

这次排查最有用的一步，是把**命令中的地址与报错中的地址放在一起比较**。认证错误只是表面现象，实际访问路径被全局 `insteadOf` 规则改变，才是继续排查的入口。通过“查看配置来源 → 临时绕过重写 → 查询目标分支 → 完整克隆 → 检查分支与远端地址”，可以逐步把猜测转化为有依据的判断。

以后遇到类似 Git 问题，我会先确认实际访问的主机与配置来源，再检查网络、仓库权限和凭据；验证修复时，也要区分本地地址解析成功与真正的远端访问成功。
