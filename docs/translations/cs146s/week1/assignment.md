## 作业概述

本周，你要让一次真实的 Claude Code 会话经过代理，捕获它实际发出的 HTTP 请求，再逐一**剖析**。这次不需要开发新功能，而是要深入阅读一个已经投入实际使用的系统，细致到能看出它背后的设计取舍。

### 学习目标

- **追踪**生产级编程 Agent 的真实会话，理解其调用结构。
- **分析**在一项有一定复杂度的编程任务中，提示词、工具 Schema 和模型响应如何配合。
- **反思**如果自己开发 Agent，哪些行为值得借鉴，哪些应当改变。

## 参考资料

- **[截获 Claude Code 请求](https://www.ai.moda/en/blog/tutorial-intercepting-claude-code-requests)**：本作业采用的技术，请先阅读。
- **[Anthropic Messages API 参考文档](https://docs.claude.com/en/api/messages)**：帮助你理解即将分析的请求结构，包括 `system`、`tools` 和 `messages`。
- **[Claude Code 设置参考文档](https://docs.claude.com/en/docs/claude-code/settings)**：介绍用户级配置 `~/.claude/settings.json` 与项目级配置 `.claude/settings.json` 的工作方式。

## 环境准备

**前提：安装并开通 Claude Code。** 斯坦福通过 SUNet ID 提供 Claude Code 访问权限。如果尚未开通，请先[申请访问权限](https://uit.stanford.edu/service/claude)，再[安装并登录](https://code.claude.com/docs/en/setup)。获批并安装完成后，运行 `claude --version` 确认安装成功，并将版本号写进报告。

### 1. 安装 mitmproxy

- **macOS**：运行 `brew install --cask mitmproxy`。
- **Windows**：从 [mitmproxy.org](https://mitmproxy.org/) 下载并运行安装程序，它会将 `mitmweb` 加入 `PATH`。
- **Linux 或其他平台**：运行 `pip install mitmproxy`。如果创建了课程 Conda 环境，请在该环境中安装。

### 2. 启动反向代理

```bash
mitmweb --listen-host 127.0.0.1 --listen-port 58888 \
        --web-open-browser --mode reverse:https://api.anthropic.com \
        -w session.flows
```

发送到 `127.0.0.1:58888` 的流量会被转发到真实 API；检查界面会在 `http://localhost:8081` 打开。反向代理模式允许你把 Claude Code 指向本地普通 HTTP 地址，因此无需安装 CA 证书。`-w session.flows` 会把每条请求与响应记录保存到磁盘。请在**任何 Git 仓库之外**的目录运行此命令，以免误将捕获文件提交。

### 3. 让 Claude Code 通过代理连接

在第一部分将使用的仓库中，创建**项目级**配置 `.claude/settings.json`：

```json
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://127.0.0.1:58888",
    "ENABLE_TOOL_SEARCH": "true"
  }
}
```

> **注意：不要将这段配置写入 `~/.claude/settings.json`！** 否则，机器上所有 Claude Code 会话都会进入捕获记录；停止 `mitmweb` 后，这些会话也会无法正常连接。

### 4. 验证配置

启动一个新的 `claude` 会话，随便发送一条消息，确认 mitmweb 中出现 `POST /v1/messages` 记录。

### 5. 作业完成后清理

删除该仓库的 `.claude/settings.json`，或仅删除其中的 `env` 配置块，并停止 `mitmweb`。

## 第一部分：捕获一次会话（15 分）

让**一次**会话经过代理，并同时满足以下四项要求：

1. **涉及多个文件**：至少修改两个文件。
2. **至少失败一次**：需要观察一次错误恢复过程。故意让测试失败，是比较可靠的做法。
3. **任务足够复杂，需要规划**：Agent 应当明确制定计划，例如创建任务列表、使用计划模式或编写计划文件，而非只调用一次工具。
4. **使用你自己的仓库**：使用临时练习项目，不要使用本作业仓库。

如果暂时没有想法，可以考虑：

- 删除一个被其他模块导入的函数，再让 Claude 恢复全部功能并通过测试。
- 为一个小型 Web 应用添加接口和测试，再要求它在一个尚未安装的依赖版本下通过整套测试。
- 重命名一个模块，让它更新全部导入，再运行 lint 检查和测试。
- 提出一项需要陌生库的功能，让 Agent 必须先查 API，才能动手实现。

在 mitmweb 界面中，选中 `POST /v1/messages` 记录，将**请求体**下载为 JSON，保存在本地。这些文件不需要提交，但后面各部分都要根据其中的证据评分，因此要保留足以支撑回答的记录。

如果 mitmweb 会话中断，可以通过 `mitmweb -r session.flows` 重新打开已保存的 `session.flows` 文件，继续分析。

### 引用前先脱敏 { #_5 }

捕获记录中包含你的源代码、文件路径和凭据。除了你有意选取、写入 `writeup.md` 的引用片段，其他内容都不应进入仓库。

- 不要粘贴原始流量记录或 HTTP 请求头，`x-api-key`、`authorization` 等凭据就在其中。
- **请求体也可能含有秘密信息。** Agent 读取过的内容，包括 `.env`、配置文件和命令输出，都会重新出现在 `messages` 中。引用工具结果前，务必检查。
- 不要把 `session.flows` 放进任何 Git 仓库。
- 删除引用中的私密信息时，要留下明确标记，例如 `[REDACTED: internal hostname]`，不能悄悄删掉。
- 如果脱敏会破坏片段的含义，请换一个用完即可丢弃的临时仓库，重新捕获。

## 第二部分：批注系统提示词（25 分）

将 `system` 配置块，以及所有 `role: "system"` 的消息，按内容拆分。逐段回答：**这段指令想促成什么行为？又在防止哪种失败？** 要做批注分析，而不是概括内容。

至少覆盖以下方面：

- **结构**：有哪些主要部分，按什么顺序排列，为什么这样安排。
- **语气与详略**：哪些具体措辞控制回复长度、格式，为什么值得为它们花费 token。
- **何时不该行动**：破坏性操作的执行条件、任务范围限制、拒绝执行的条件。
- **环境上下文**：Agent 获知了哪些机器、仓库、会话信息，它们放在请求的哪里。

另外，专门分析 `<system-reminder>`：它出现于 `system` 块、消息列表，还是两者都有？请举例证明。你能找到哪些证据，说明它至少承担了两种不同用途？为什么在对话中途注入，而不是只在开头说一次？

## 第三部分：批注工具设计（25 分）

**工具清单要给数字，不能只作描述。** 统计可用工具总数，并区分内置工具、MCP 提供的工具，以及延迟加载或可搜索发现的工具。记录不同请求之间工具集合是否变化，以及由什么触发。好的回答应当像“首次请求共有 117 个工具：35 个内置工具，另外 82 个来自三个 MCP 服务器”，而不是“可用工具很多”。

**设计分析。** 选择**两个**工具，将其当作接口设计来分析：

- 引用相关的 Schema 片段。
- 为什么采用这组参数？哪些必填、哪些可选，哪些能力刻意不向模型开放？
- 工具描述在防范什么问题？成熟 Agent 的工具描述，往往是反复踩坑后积累的经验。找出一句明显是为了纠正模型反复犯错而写的说明，并指出它要防止什么错误。
- 这个工具刻意不做什么？这又说明外围系统承担了哪些职责？

两个工具应当有明显差别。只选两个文件操作工具，说服力较弱；把文件工具与编排工具搭配，或选择一个失败处理约定独特的工具，会更有分析价值。

## 第四部分：基于证据分析行为（25 分）

根据你自己的调用轨迹回答。每项回答都必须**注明证据位置**，包括请求、消息索引、工具调用，并**标为 `[OBSERVED]` 或 `[INFERRED]`**。`[OBSERVED]` 表示直接观察到，能在捕获记录中指出；`[INFERRED]` 表示没有亲眼看到发生，而是根据定义和机制推断。两者都可以，但不能混淆；未标注的回答不得分。

- **错误恢复**：完整梳理一次失败。Agent 看到了什么，随后尝试什么，恢复用了多少轮？相关内容必须逐字引用。
- **规划**：来自工具、提示词指令、自发行为，还是几者共同作用？什么证据能区分这些可能？
- **计划与任务状态**：如何创建，又如何推进？每轮模型能看到哪些任务状态信息，它们放在请求的哪里？
- **子 Agent**：何时委派任务？子 Agent 获得哪些信息，又返回什么？如果本次会话没有触发子 Agent，如实标为 `[INFERRED]` 即可。
- **上下文管理**：随着会话变长，请求载荷发生什么变化？早期轮次如何在后续请求中表示？

## 第五部分：反思（10 分）

不超过一页，说明：**两项你会借鉴的设计**，以及各自解决的问题；**一项你会采用不同做法的设计**，同时认真分析原设计可能存在的理由；还有**一条这次轨迹分析带来的改变**，说明今后日常使用编程 Agent 时，你会怎样调整引导方式。
