# 第 11 章　Agentic-RL

*Hello-Agents：从零开始构建智能体 · 章节学习笔记*

<a id="introduction"></a>

## 引言

之前的章节主要调整提示、工具和控制流程，模型参数通常没有变化。如果我们希望模型更稳定地遵循输出约定，或更倾向于选择能完成任务的路径，就可能需要训练。

本章用数学题作为一个便于自动核对的小环境，串起数据准备、监督微调、奖励优化和评估。这个训练入口能说明方法，但不能单凭数学题训练，就认为已经完成通用工具智能体的训练。

<a id="section-11-1"></a>

## 11.1　从一次回答，到行动策略

在强化学习中，策略决定当前状态下怎样行动，奖励用来评价结果。对于语言模型，行动可以是生成文本，也可以在更完整的环境里选择工具、处理反馈并继续工作。

Agentic RL 关注这种多步过程：只评价最后一段话，可能漏掉中间的错误调用、重复操作或无效探索。环境、状态和奖励都需要与真正要完成的任务对应。

原文使用 TRL、Qwen3-0.6B 与 GSM8K 搭建训练示例，由 `RLTrainingTool` 统一组织相关操作。这些是本章案例的技术选择，不是所有训练任务必须采用的组合。

<a id="section-11-1-1"></a>

### 11.1.1　状态、动作与轨迹怎样映射到语言任务

在数学示例中，状态包含题目和已有输出，动作是继续生成内容，最终答案由程序评价。在工具任务中，状态还包括查询结果，动作则可能在文本生成与工具调用之间切换。

轨迹记录从初始问题到结束发生了什么。只有最终回答时，难以知道错误来自哪一步；保留中间动作以后，才能研究重复查询、无效参数或过早结束等行为。

奖励因此可以针对终局，也可以辅助评价中间过程。但增加中间奖励必须与最终目标一致。例如，每调用一次工具就加分，可能鼓励不必要的调用。能产生数值反馈，并不表示反馈设计已经合理。

<a id="section-11-2"></a>

## 11.2　先把数据和成功标准准备好

GSM8K 包含数学应用题及解答，便于提取最终数值并与参考答案比较。同一份原始数据，会根据训练方式转换成不同格式。

| 阶段 | 通常需要的数据 | 学习信号 |
| --- | --- | --- |
| SFT | 问题与示范回答。 | 更接近示范中的输出。 |
| 奖励训练 | 问题、用于核对的答案及评分函数。 | 当前生成的结果获得多高评价。 |
| 测试 | 未用于训练和调参的问题。 | 衡量对新问题的表现。 |

答案抽取也属于系统的一部分。模型算对了，却因为解析器读错位置而得零分，是格式与评价问题；需要与真正的计算错误分别分析。

<a id="section-11-2-1"></a>

### 11.2.1　奖励会引导模型学什么

本章介绍准确率、长度和步骤等评分。准确率比较结果，长度项控制生成开销，步骤项鼓励某些输出结构。

不过，出现很多步骤不等于推导正确，文本更短也不总是更好。若奖励容易被表面格式满足，模型就可能优化评分器，而没有改善任务效果。

可以先用少量正确、错误和刻意偏离要求的样例测试奖励函数，再开始训练。定义好“什么算成功”，通常比先调很多训练参数更重要。

<a id="section-11-2-2"></a>

### 11.2.2　数据转换时保留题目与答案的对应关系

GSM8K 的原始样本同时包含问题与解答，转换时需要决定哪些内容作为输入、哪些作为监督输出，以及最终答案怎样抽取。若把答案意外放进评测输入，会得到失真的高分。

```text
原始问题与解答
  ├─ SFT：形成问题到示范回答的训练样本
  ├─ RL：提供问题，并保留评分所需参考答案
  └─ 测试：输入问题，生成以后再与参考结果核对
```

训练、调参与最终测试也要分开。验证集帮助选择配置，测试集回答选择完成后的新任务表现。反复用同一小批题修改提示或奖励，等于逐渐把它们变成开发资料。

<a id="section-11-2-3"></a>

### 11.2.3　组合奖励时先明确尺度

准确率奖励可能只取 0 或 1，长度惩罚却可能随 token 数累积。如果二者尺度差别过大，模型可能更关注压缩长度，而不愿完成必要推导。

可以先分别观察每个分量，再决定权重。训练日志也应保留分量变化：总奖励增加，究竟因为答得更准、文本更短，还是格式项更多？只有总分时，很难看出这种差别。

<a id="section-11-3"></a>

## 11.3　SFT：给模型一个较好的起点

监督微调（Supervised Fine-Tuning）让模型学习问题与示范回答的对应关系。在本章流程中，它帮助模型熟悉数学任务和约定格式，再进入奖励训练。

SFT 是这套实践安排中的起点，不是所有强化学习方案在理论上都必须执行的步骤。能否从某个基础模型直接开始，还要看它已有能力和奖励信号。

<a id="section-11-3-1"></a>

### 11.3.1　LoRA 为什么能减少训练参数

LoRA 冻结原权重，使用低秩矩阵表示增量。若原权重是 $W$，可以写成：

$$
W'=W+BA,
$$

其中中间维度远小于原矩阵维度，因此可训练参数减少。它不是把原模型变成一个很小的模型，前向计算和激活等仍会消耗资源。

训练时需要共同考虑数据长度、批次、累积步数、精度和优化器等设置。示例中的显存与速度只能在对应条件下理解，不能只由参数量推算全部开销。

<a id="section-11-3-2"></a>

### 11.3.2　一个低秩更新能减少多少参数

假设某权重矩阵是 `1000 × 1000`，共有一百万个元素。若采用秩为 8 的分解，新增矩阵分别是 `1000 × 8` 和 `8 × 1000`，合计 16000 个可训练元素，即原矩阵数量的 1.6%。

这个例子只计算该矩阵的参数，不是整套训练的显存比例。激活、优化器状态、生成样本和其他模块依然有成本。参数高效与整个任务几乎不耗资源，是两件事。

低秩更新也可能影响不同任务表现。选择哪些层、采用多大秩以及训练多少数据，都需要结合验证，而不应只追求更少参数。

<a id="section-11-3-3"></a>

### 11.3.3　损失下降以后，还应观察什么

训练损失下降说明模型更适应当前训练目标，但可能同时过拟合。可以固定一组未用于更新的题目，定期比较答案、格式与长度，并保存对应检查点。

还要核对模型是否真的生成到最终答案。若输出经常被上限截断，低正确率可能与生成配置有关；若格式正确却数值错误，则需要查看推理与计算问题。训练曲线和实际样例应一起阅读。

<a id="section-11-4"></a>

## 11.4　GRPO：比较同一问题的多份尝试

GRPO 为同一个问题采样多份回答，逐一评分，再使用组内相对表现形成更新信号。这样，不必为优势估计单独训练传统的价值网络。

**示例 11.1　为什么需要同组比较**

```text
同一道题生成四份回答
  → 两份答案正确，两份错误
  → 计算各自奖励与组内基准
  → 鼓励表现相对较好的生成行为
  → 限制过大的策略变化，再继续采样
```

常见实现会使用组内均值与标准差进行归一化，也会结合策略更新约束或参考策略项。原文的简化公式帮助理解相对评价，具体损失与实现选项仍要对照训练库版本。

<a id="section-11-4-1"></a>

### 11.4.1　训练信号也可能不足

若一组回答全错或全对，按组内相对奖励形成的区分信号可能很弱。采样数量、题目难度和生成多样性因而会影响训练，而不是简单地设置越大就越好。

还要监控平均奖励、生成长度与策略变化。分数上升可能是效果改善，也可能是学会利用评分漏洞，需要查看实际样例才能判断。

<a id="section-11-4-2"></a>

### 11.4.2　用四个奖励理解组内比较

假设同一问题的四份回答得到 `1、0、1、0`，平均奖励是 0.5。若用总体标准差 0.5 作归一化，相对分数便约为 `1、-1、1、-1`。高于组内平均的回答得到正向信号，低于平均的得到负向信号。

若四份都是 0，组内就缺少哪一份更好的差别。这不是通过提高训练步数就一定能解决的问题，可能需要调整任务难度、初始化能力或奖励。

相对评分只提供更新方向，策略更新还会考虑生成概率等量。它不是直接把高分文本复制进模型，也不是保证每次更新之后所有问题都更好。

<a id="section-11-4-3"></a>

### 11.4.3　参考策略与探索之间的取舍

本章使用参考策略和相应约束，帮助限制模型在训练中偏离过大。变化太小，可能改善有限；变化太大，又可能破坏已有能力或利用奖励漏洞。

生成温度与每题采样数量影响探索。更多候选通常带来更多计算，但有价值的差异还取决于题目和当前策略。观察组内奖励分布，有时比单独看采样数量更能说明训练信号。

<a id="section-11-5"></a>

## 11.5　怎样判断训练确实有帮助

应在相同测试条件下比较基础模型、SFT 模型和奖励训练后的模型，同时记录准确率、时延、长度与失败类型。

计算错误、题意理解错误、推理安排错误和格式错误，需要不同改进方法。若主要问题是答案抽取，继续加训练步数未必有效；若困难题表现差，则需要检查数据覆盖和奖励是否提供足够信息。

多次采样后至少有一次答对，与单次回答正确率也不同。报告指标时，应说明允许了多少次尝试，避免把额外计算带来的收益当作同等成本下的提升。

<a id="section-11-5-1"></a>

### 11.5.1　把错误归到可以行动的类别

理解错误需要核对题意，计算错误可以借助可验证运算，格式错误需要检查示范与解析，推理安排错误则要看中间依赖。不同错误比例有助于决定下一轮改数据、改奖励还是改输出处理。

评估还可以按题目难度或任务类型分组。总分上升可能只来自简单题更稳，复杂题仍未改善；如果应用主要面对复杂任务，平均分就不足以支撑上线判断。

多次尝试的结果也应与单次结果分开。允许五次生成后选出正确答案，消耗的计算与只生成一次不同，比较时需要同时说明成功率和预算。

<a id="section-11-6"></a>

## 11.6　把训练流程连接到部署

本章的完整流程是准备数据、SFT、检查 SFT 结果、GRPO、再次评估，最后保存并部署模型。调参可以使用网格、随机搜索或其他优化方法，但应在验证集上选择，保留测试集用于最终评价。

多卡和分布式工具帮助处理较大任务，也带来通信与配置成本。保存时应保留基础模型、分词器、适配器和数据配置的对应关系；需要时再合并 LoRA 权重。

<a id="section-11-6-1"></a>

### 11.6.1　批次、梯度累积与多卡怎样配合

在常见数据并行设置下，有效批次可以按“每设备批次 × 梯度累积步数 × 设备数”理解。每卡 2 个样本、累积 4 步、使用 2 卡时，一次更新对应 16 个样本。

梯度累积让较小的单次批次参与同一次更新，但不会让单个长序列的内存需求消失。多卡还会引入同步和通信，不能只按卡数推断速度同比增加。

<a id="section-11-6-2"></a>

### 11.6.2　导出后检查的是哪一份模型

LoRA 适配器需要与正确的基础模型配合，合并后的权重也应保留版本。分词器、聊天模板和推理配置同样影响结果，不能只拷贝一个权重目录就忽略其他部分。

部署时可以重新运行固定样例，比较导出前后答案与格式，再测延迟和资源使用。量化、批处理或服务化可能改变运行行为，因此部署评价不是离线训练评价的重复，而是检查另一段实际链路。

训练完成后还要验证实际服务中的行为。离线数学得分有价值，但若最终应用要搜索网页或处理订单，还需要相应环境和端到端评估。下一章会专门讨论怎样组织这类评价。
