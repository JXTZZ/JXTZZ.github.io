## 引言

第一章的旅行助手在终端里查天气、找景点。这一章把同一类需求做成完整应用：用户填写日期和偏好，系统查询资料、生成计划，再用地图和日程页面展示出来。

变化不只是多了一个界面。信息要经过表单、后端、多个智能体和外部服务，还要支持编辑与导出。把这些环节之间的数据约定讲清楚，正是本章的重要内容。

<a id="section-13-1"></a>

## 13.1　让一份行程穿过整个应用

原文采用 Vue 3 与 TypeScript 处理前端交互，FastAPI 接收请求，HelloAgents 组织规划过程，再连接高德地图、图片和模型服务。

```mermaid
flowchart LR
    A[用户填写出游要求] --> B[后端验证请求]
    B --> C[收集景点、天气与酒店资料]
    C --> D[整合行程计划]
    D --> E[结构与字段检查]
    E --> F[页面、地图与编辑]
```

可以先沿着一次请求看源码：用户输入怎样进入 `TripPlanRequest`，查询结果怎样参与规划，最后怎样成为前端需要的 `TripPlan`。这样比同时阅读所有页面与工具类更容易把握关系。

<a id="section-13-1-1"></a>

### 13.1.1　从表单提交到页面返回

用户在首页选择城市、日期与偏好，前端先组织请求，再交给后端。后端将请求转换为约定对象，调用协调器取得行程，补充页面需要的数据，最后序列化返回。

这段链路可以按层定位问题。表单没有收集预算，是输入问题；后端没有传给规划器，是数据传递问题；规划器收到但没有遵守，是生成或检查问题。最后页面显示错误，还可能是字段映射与状态更新的问题。

一次失败不一定需要重新设计整个多智能体系统。沿着同一份输入逐层查看，能够知道用户要求是在何处丢失或被改变的。

<a id="section-13-2"></a>

## 13.2　先约定行程数据的结构

外部服务可能使用不同经纬度字段，价格也可能用字符串或区间表示。若这些差别一路传到页面，处理逻辑就会散落各处。

本章从基础位置模型开始，逐步组合景点、酒店、餐饮、每日计划和完整行程。Pydantic 定义字段与约束，FastAPI 借助这些模型进行请求和响应处理，前端再定义相应 TypeScript 类型。

<a id="section-13-2-1"></a>

### 13.2.1　结构正确与事实正确

经度在合法范围、价格能够解析为数字，只能说明部分数据形态符合要求。景点是否真实开放、价格是否对应游览日期，仍需要资料支持。

同样，模型生成了一段可解析 JSON，也不保证每天的安排能够实际完成。结构验证之后，还需要检查日期、时间、地点与预算之间是否一致。

<a id="section-13-2-2"></a>

### 13.2.2　嵌套模型怎样表达一份完整行程

`Location` 提供经纬度，`Attraction` 引用位置并加入门票等字段，`DayPlan` 再组合当天景点、住宿与其他安排，`TripPlan` 保存城市、起止日期和每日计划。

```text
TripPlan
  ├─ city、start_date、end_date
  ├─ days
  │   └─ DayPlan
  │       ├─ attractions → Attraction → Location
  │       ├─ hotel
  │       └─ 其他日程信息
  ├─ weather_info
  ├─ overall_suggestions
  └─ budget
```

一个地方统一定义经纬度，比在每个页面分别拆解字符串更容易维护。新增字段后，也能知道哪些模型和页面依赖它，而不必在所有字典中猜测。

<a id="section-13-2-3"></a>

### 13.2.3　转换、默认值与验证怎样配合

外部天气可能把温度写成带单位的字符串，可以在模型入口统一转换，再让内部使用数值。缺少酒店信息时，也可以明确表示为空，而不是生成一个占位酒店。

默认值要符合业务含义。门票字段默认 0，有时只是表示没有取得价格，并不证明免费。若界面需要区分“免费”和“未知”，就应在数据中保留不同状态。

字段类型正确以后，还应检查字段之间的关系，例如结束日期不能早于开始日期，每日计划不能悄悄超出请求区间。这类跨字段判断，是结构模型之后的重要一层。

<a id="section-13-3"></a>

## 13.3　四个角色怎样分工

| 角色 | 输入与工作重点 | 输出供谁使用 |
| --- | --- | --- |
| `AttractionSearchAgent` | 城市与兴趣偏好，查询有关景点。 | 交给规划角色。 |
| `WeatherQueryAgent` | 城市与可获得的天气信息。 | 帮助安排活动。 |
| `HotelAgent` | 目的地与住宿需求，查询候选酒店。 | 交给规划角色。 |
| `PlannerAgent` | 用户约束及前三类资料。 | 生成完整结构化行程。 |

前三个角色获取不同资料，规划角色负责整合。本章的基础协调器按顺序执行查询，再汇总到规划请求中；多角色并不意味着已经实现并行调度。

<a id="section-13-3-1"></a>

### 13.3.1　怎样把信息交给规划角色

规划输入应保留用户原始要求，再分区放入景点、天气和住宿资料。不能为了节省文本，把预算或日期这类关键条件丢掉。

如果天气服务不能覆盖整个未来行程，应保留这一限制；酒店搜索结果也不等于已取得对应日期的可预订报价。规划角色需要使用已知信息，而不是补出缺失事实。

分工的好处在于每个角色较容易单独调试。它们并不必然比单 Agent 更好，主要作用是把信息收集与整合职责显式分开。

<a id="section-13-3-2"></a>

### 13.3.2　资料收集与行程整合怎样交接

景点角色返回候选列表，天气角色返回预报，酒店角色返回住宿线索，最后由规划角色共同使用。三个查询之间不必依赖前一个生成的文字，真正的汇合点是规划输入。

交接时可以保留结构、来源与查询条件，而不只保留一段概述。某个酒店是在什么城市、按什么要求找到的，都会影响规划角色能否正确使用。

若某一路没有结果，协调器应明确传递缺失项。规划角色可以调整安排或说明限制，但不应把“没有查到”写成一个确定推荐。多角色分工减少单个提示负担，也增加了这种交接责任。

<a id="section-13-3-3"></a>

### 13.3.3　规划以后还要检查地理与时间

一天安排的景点，即使全部真实，也可能分布过远。可以结合位置和交通信息检查是否合理，再考虑停留时间、餐饮和开放时段。

原文基础案例着重展示生成与展示链路。继续完善时，可把这些可计算条件独立出来检查，再把不满足之处交给规划角色调整。这样，地图不仅是装饰，也能参与验证计划。

<a id="section-13-4"></a>

## 13.4　共享工具连接，而不是重复启动服务

本章使用高德地图 MCP 服务提供地点信息（POI）、天气等工具。几个角色共享一个 `MCPTool` 实例，避免为相同服务重复创建进程。

共享有助于集中管理连接和资源，但并不会自动保证请求限流或并发安全；这些仍取决于服务与应用的实现。也可以把 HTTP API 包装成普通工具，MCP 的价值在于复用共同接口与已有服务。

图片则由独立的 Unsplash 服务获取，再补充到行程数据。图片能改善阅读体验，却可能与同名地点混淆，因此不能作为确认景点身份的唯一依据。

<a id="section-13-4-1"></a>

### 13.4.1　共享连接之后，谁负责管理它

共享 MCP 实例可以避免重复启动相同服务，但需要有清楚的创建与关闭位置。若每次请求都重新建立连接，仍可能反复消耗启动时间；若永远不关闭，又可能留下无用资源。

几个角色调用同一服务时，还应保留调用来源，便于区分景点搜索和酒店搜索的结果。并发扩展以后，工具参数和返回关联也需要正确维护。

图片服务提供的是另外一类补充内容。没有合适图片时，页面可以使用清楚的占位展示；图片查询失败不应使已经有效的行程文本整体丢失。不同外部能力可以采用不同的降级方式。

<a id="section-13-5"></a>

## 13.5　前端怎样让计划便于使用

首页表单收集目的地、日期、偏好、交通与住宿要求，结果页再展示概览、预算、地图和每日安排。API 服务封装请求，页面不必直接知道后端内部怎样调度角色。

地图使用地点坐标创建标记，列表显示具体行程。两种表示应引用同一份数据，避免地图上的顺序与文字内容不同。

<a id="section-13-5-1"></a>

### 13.5.1　编辑时保留可撤销的原稿

用户可能删除景点、改变顺序，也可能取消修改。因此，编辑前保留独立副本，取消时恢复，保存时再更新当前计划。

原文用深拷贝演示这种状态分离。编辑完成后，地图和相关统计也需要同步；若改变了停留天数或费用项目，就不能只移动页面上的一张卡片。

<a id="section-13-5-2"></a>

### 13.5.2　编辑行程后，哪些信息需要一起变化

删除一个景点，至少会改变列表与地图标记；调整顺序，还会影响编号与可能的路线；改变天数，则可能牵动住宿与预算。将它们都绑定到同一份计划状态，才能减少页面之间的不一致。

原稿与编辑稿分离，也让取消操作有明确依据。保存时再统一更新派生信息，比每拖动一次卡片就分别修改多个不相关变量更容易控制。

前端类型有助于开发时发现字段拼写错误，运行时收到的数据仍需要核对。类型声明本身不会把一个错误 API 响应变成合法对象。

<a id="section-13-6"></a>

## 13.6　几个容易被界面掩盖的细节

<a id="section-13-6-1"></a>

### 13.6.1　预算是估算，还需要一致性检查

原文让规划角色输出景点、住宿、餐饮和交通四类预算。模型可以组织费用解释，但总额最好由程序根据明细复算，并明确金额单位、人数和住宿晚数。

这项复算属于进一步完善的方向，不能把原文的生成式预算直接理解成交易系统的结算结果。

**示例 13.1　把人数、晚数和金额单位说清楚**

假设两人出行三天两晚，以下金额仅用于说明计算：

| 项目 | 计价方式 | 合计 |
| --- | --- | --- |
| 门票 | 每人共 80 元，两人。 | 160 元 |
| 住宿 | 一间房每晚 300 元，共两晚。 | 600 元 |
| 餐饮 | 每人每天 90 元，两人三天。 | 540 元 |
| 交通 | 本次行程统一估算。 | 200 元 |
| 总计 | 四项相加。 | 1500 元 |

如果删除每人 20 元的景点，门票合计减少 40 元，住宿不会因此自动减少一晚。这说明预算需要明确计价对象，不能只对所有数字统一求和。

程序可以检查明细与总额一致，再让模型解释方案。若某项只是估算，还应保留估算身份，避免页面上的精确数字制造已经核实报价的印象。

<a id="section-13-6-2"></a>

### 13.6.2　进度展示应与真实状态对应

本章示例使用模拟进度改善等待体验。它提示程序仍在工作，但不是后端已完成比例的准确测量。需要更精确反馈时，可改为上报当前查询或规划阶段。

<a id="section-13-6-3"></a>

### 13.6.3　导出与屏幕显示不是同一回事

原文使用 `html2canvas` 与 `jsPDF` 导出图片或 PDF，并讨论地图 Canvas 与跨域带来的限制。当前简化方案在导出时隐藏地图，静态地图或服务端截图则是可继续研究的方向。

<a id="section-13-6-4"></a>

### 13.6.4　怎样检查一次完整规划是否可用

可以先准备一组明确请求：固定城市、日期、人数和偏好，再依次检查请求验证、查询结果、生成结构与前端展示。这样，失败时容易知道是哪一层需要修改。

还可以加入一种缺失情况，例如天气暂时不可得，观察应用是否保留其他已取得资料并说明限制。编辑、取消与导出也分别检查，避免把“生成成功”当作整个产品已经完成验证。

这类任务贯穿模型与普通软件。模型负责组织建议，数据结构保证传递一致，工具取得外部信息，界面让用户检查和修改。内容丰富的应用，最终仍依赖这些部分共同工作。

这些细节说明，一份模型结果要变成可使用的产品，还需要状态管理、数据验证和交互设计。下一章换到研究任务，继续讨论怎样展示更长的执行过程。
