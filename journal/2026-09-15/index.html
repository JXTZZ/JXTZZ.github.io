    今天处理了两个 Windows 开发环境问题：wsl --install 持续返回 403，安装 Miniconda 后普通 PowerShell 又无法识别 conda。前者通过从本地文件安装完成，后者通过初始化 PowerShell 解决。

    WSL 在线安装持续返回 403¶

    重新安装 WSL 时，在 PowerShell 中执行：

    wsl --install

    得到以下错误：

    已禁止 (403)。

    当时 Windows 已开启 Clash Verge。随后尝试绕过 Microsoft Store 的下载方式：

    wsl --install --web-download -d Ubuntu

    结果仍然是 403，说明仅更换这条下载路径没有解决问题。

    检查代理后，仍未找到 403 的具体来源¶

    先查看 WinHTTP 代理配置：

    netsh winhttp show proxy

    最初显示“直接访问（没有代理服务器）”。Windows 的系统代理与 WinHTTP 代理是不同的设置，前者开启并不保证后者也已配置。本次在管理员 PowerShell 中导入系统代理，再次检查：

    netsh winhttp import proxy source=ie
netsh winhttp show proxy

    此时能看到本机 Clash 的代理地址 127.0.0.1:7897。又确认系统代理与 TUN 模式已开启，并临时尝试全局模式，在线安装仍返回 403。

    这些检查只确认了相应设置，尚不足以证明每个下载请求都经过代理，也没有定位到拒绝请求的具体服务。于是先保留这个未解原因，改用本地安装包完成环境配置。导入 WinHTTP 代理是本次排查中尝试过的步骤，不是离线安装的前置要求。

    从本地文件安装 WSL 与 Ubuntu¶

    这里的“离线安装”指安装时不再依赖 wsl --install 自动下载组件。安装包仍需提前获取，也可以在另一台能正常下载的电脑上准备。微软的离线安装说明提供了 WSL MSI 与发行版镜像的入口。

    本次按以下步骤处理：

    1. 在管理员 PowerShell 中启用相关组件：

      dism.exe /online /enable-feature /featurename:Microsoft-Windows-Subsystem-Linux /all /norestart
dism.exe /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart

      这是本机当时的启用步骤。当前 WSL 2 离线安装文档列出的必需可选组件是虚拟机平台；是否还需要 WSL 可选组件，应结合安装方式与 WSL 1 需求判断。

    2. 保存工作并重启 Windows。

    3. 从 microsoft/WSL Releases 下载与系统架构匹配的 MSI 安装包，完成安装后检查：

      wsl --version

    4. 从官方发行版信息中的下载入口准备 Ubuntu .wsl 镜像。下载入口可在 DistributionInfo.json 中查找。然后安装本地文件，路径和名称按实际情况替换：

      wsl --install --from-file "D:\Downloads\ubuntu-24.04.wsl" --name Ubuntu-24.04

      此命令需要支持 .wsl 安装格式的 WSL 版本。若提示选项未知，先检查 WSL 版本及 wsl --help。

    5. 检查发行版并启动：

      wsl -l -v
wsl -d Ubuntu-24.04

    本次安装后能够进入 Ubuntu 终端，完成了环境恢复。这验证了本地安装方案可用，在线下载持续返回 403 的具体原因仍未确认。

    首次启动时的 localhost 代理警告¶

    Ubuntu 首次启动时还有一条提示：

    wsl: 检测到 localhost 代理配置，但未镜像到 WSL。
NAT 模式下的 WSL 不支持 localhost 代理。

    在 NAT 模式下，WSL 内的 127.0.0.1 指向 Linux 环境自身，不能直接用它连接 Windows 上的回环代理。警告描述的是网络配置问题，发行版仍可能已经安装成功。

    如果满足 Windows 11 22H2 及相应 WSL 版本条件，可以参考 WSL 网络配置启用镜像网络与自动代理。保存 WSL 中的工作后，在 Windows PowerShell 中执行 wsl --shutdown，再重新打开发行版。连接方式与系统条件见微软网络文档。

    Miniconda 安装后，普通 PowerShell 找不到 conda¶

    Miniconda 安装后，普通 PowerShell 无法识别 conda，但 Anaconda PowerShell Prompt 中可以使用。这说明 Conda 已可运行，普通终端还没有加载相应的 shell 初始化代码。

    在能使用 Conda 的 Anaconda PowerShell Prompt 中执行：

    conda init powershell

    然后关闭并重新打开普通 PowerShell。可用下面的命令检查是否已接入：

    conda --version
conda info --envs

    conda init 会修改 shell 初始化配置，使后续会话能够使用 conda activate 等命令。见 Conda 初始化说明。

    如果希望能使用 Conda，但不想每次打开终端都自动进入 base，可以设置：

    conda config --set auto_activate_base false

    因此，是否显示 (base) 不能单独用来判断初始化是否成功。需要分别检查命令能否识别，以及环境能否正常激活。
